# Contributing to Quoter

Bug reports, feature requests, reproduction details and focused contributions
are welcome. The [issue tracker](https://github.com/Damercy/Quoter/issues) is the
public request ledger; [ROADMAP.md](ROADMAP.md) summarizes the release direction.

## Requests and updates

Search existing issues first. Add a thumbs-up reaction to a request you support
and comment with new use cases or evidence. Otherwise, use the
[feature request](https://github.com/Damercy/Quoter/issues/new?template=feature-request.yml)
or [bug report](https://github.com/Damercy/Quoter/issues/new?template=bug-report.yml)
form. A GitHub account is needed to participate.

Anyone can submit a request, update their report and join the discussion.
Maintainers manage labels, milestones, acceptance and release priority. Reactions
help gauge interest; they are not a delivery promise. Duplicates link to the
original issue, and declined requests retain a brief explanation. Be considerate
and keep discussion focused on the problem and proposed behavior.

Never post credentials, signing files, private contact information or unsanitized
logs. Use [private reporting](SECURITY.md) for security vulnerabilities.

## Pull requests

Small fixes, documentation corrections and focused pull requests are welcome.
Discuss significant features or visual changes in an issue before implementing
them. Include the use case, scope and relevant validation; link the issue.
Roadmap wording can also be proposed through a pull request, with maintainers
reviewing changes to priority or release scope.

Follow [development guidance](AGENTS.md), the
[design direction](audit/DESIGN-DIRECTION.md) and the [CI guide](audit/CI.md).
Keep Quoter monochrome and accessible. Describe emulator evidence accurately;
physical-device behavior needs physical validation. Keep credentials outside Git.
Do not update visual baselines just to hide failures.

## Maintaining the ledger

Triage requests using the process in [ROADMAP.md](ROADMAP.md). Keep implementation
checklists and linked PRs on the issue, so comments and progress have one home.
Update the roadmap when priorities change, and the changelog/release notes when
work ships. Keep completed issues, milestone history and published tags.
